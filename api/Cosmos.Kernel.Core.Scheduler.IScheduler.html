Interface IScheduler

Namespace
Cosmos.Kernel.Core.Scheduler

A scheduling policy: everything that decides which thread runs when. The mechanism around it (the thread registry, the lifecycle transitions, the timer-tick entry, the register save and restore) is fixed. Install an implementation with SetScheduler(IScheduler).

Every hook runs in the kernel's most sensitive window. Most are called with interrupts already masked, and the two scheduling hooks run inside the timer interrupt itself; each member below says which. No hook may block, park, or wait, and none may allocate on the tick path. Four get no mask from the manager (SetPriority(PerCpuState, SchedulerThread, long), GetPriority(SchedulerThread) and the two run-queue diagnostics) and must take MaskInterrupts() themselves before touching the run structure. The spinlock around SetPriority(PerCpuState, SchedulerThread, long) is not a substitute: it excludes another caller, not the tick.

Several hooks have no mechanism-side caller yet, because the kernel runs on one CPU and nothing in-tree sets priorities. Implement them, but do not expect them to be exercised.

Two rules hold for every hook. Each must tolerate being called more than once for the same thread, and each must tolerate an empty SchedulerData slot, because OnThreadExit(PerCpuState, SchedulerThread) clears it and a thread can lose its record between a tick and the hook that observes it; that is why a hook reads the slot with as and never a cast. A record written by a different policy is never handed to a hook: SetScheduler(IScheduler) re-homes every live thread through OnThreadExit(PerCpuState, SchedulerThread) on the outgoing policy and OnThreadCreate(PerCpuState, SchedulerThread) on the incoming one.

Inspired by Ekiben's EkibenScheduler trait.

GetRunQueueCount(PerCpuState)

Report how many threads are waiting in the run structure. Read-only introspection for the SchedulerInfo facade, called from thread context with no guard, so guard it yourself with MaskInterrupts() if a concurrent tick could be mutating the structure underneath it. Masking inside the hook makes one call atomic and no more: a caller that counts and then reads each index needs its own mask around the whole walk, or the tick can rotate the queue between the calls.

OnThreadCreate(PerCpuState, SchedulerThread)

Allocate this policy's per-thread bookkeeping into SchedulerData on thread. Do not queue the thread yet: OnThreadReady(PerCpuState, SchedulerThread) does that. Called with interrupts masked, once for a new thread and once for every live thread the policy inherits through SetScheduler(IScheduler). An inherited thread arrives in whatever state it is in: Ready ones are handed to OnThreadReady(PerCpuState, SchedulerThread) right after, blocked and sleeping ones come back through it when they wake, and a Running one keeps running and must be accounted as runnable without being queued. The boot thread arrives that way at startup as well.

OnThreadReady(PerCpuState, SchedulerThread)

Make the thread runnable: place it and insert it into the run structure. Called for a first start, for a wake, and for a sleep expiry, so it arrives both from thread context with interrupts masked and from interrupt context, either the timer tick waking a sleeper or a device ISR signalling a waiter. It is the hook most likely to fire twice for one thread, so guard against inserting it twice.

Returns

The thread to switch to, or null to fall back to the CPU's idle thread. Remove the thread you return from the run structure: the manager re-inserts the outgoing thread through OnThreadYield(PerCpuState, SchedulerThread) after this call, and does not remove the incoming one, so leaving it queued grants it a second turn.
